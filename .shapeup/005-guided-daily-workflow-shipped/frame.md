# Frame: 日常流程引导化与 JSON 状态记忆

**Record ID**: 005
**Feature ID**: 005-guided-daily-workflow
**Created**: 2026-06-09
**Status**: Shipped — 2026-06-11

---

## Problem

OpenFlow 的日常页面已经能导入需求 JSON、创建目录、添加素材、校验尺寸数量、反馈缺失/额外素材并执行重命名。但真实使用时，JSON、尺寸预览、素材处理和页面反馈之间的职责有些缠在一起，导致高频流程不够顺。

用户这次反馈的核心是：

- JSON 是给系统理解需求用的依据，不应该在添加文件后继续干扰用户处理文件。
- 页面上的缺失、增多、非需求素材等反馈是给用户看的操作提示，不应该让用户感觉“处理文件被 JSON 卡住”。
- 导入 JSON 后，今日导入状态没有被记住；应用误关或同一天重开后，用户还要重新导入一次同一份 JSON。
- 今日导入的 JSON 只应该保留在当天/24 小时内；按现实世界时间判断，明天打开软件就应该重新导入。
- 导入 JSON 时，尺寸预览不应该承担反馈职责；现在每次导入 JSON，对应尺寸都会被点亮，看起来像页面在替用户做了额外选择。
- 添加素材目录后，如果目录里还没有任何素材，点击校验时不应该先逐个尺寸显示“缺 1 张”；更自然的首要反馈是“缺失文件”或“素材目录为空”，再补充需求总缺口。
- 日常页面当前像可拖拽面板集合，布局对高频使用来说偏繁琐；用户希望它更像一个直接的引导式流程。

当前 workaround 是用户每次打开应用后重新导入 JSON，手动理解尺寸预览中哪些点亮来自需求、哪些来自素材目录，遇到缺失、额外素材或空目录时再自己判断哪些是可继续处理的信息、哪些是真正阻塞处理的错误。这个过程能工作，但在日常交付里会反复增加判断成本。

这个 frame 的重点不是“新增更多校验规则”，而是锁定一个产品问题：日常主流程里，需求数据、素材状态和用户下一步动作的边界不够清楚，导致页面既像配置面板，又像反馈面板，还像流程工具。

## Affected Segment

主要受影响者是 OpenFlow 的日常主流程用户，也就是每天或高频处理广告素材的人：

- 从网页/插件导出需求 JSON。
- 打开桌面端，导入今日需求。
- 创建今日目录或使用已有项目目录。
- 添加素材目录。
- 查看缺失、额外、尺寸错误等反馈。
- 在可接受的风险内继续重命名已有素材。

这个问题在以下场景更明显：

- 用户误关应用或系统重启后，需要恢复刚才的工作上下文。
- 同一天反复处理同一份需求 JSON。
- JSON 抓取结果与本地素材不完全一致，页面需要告诉用户缺失或增多，但不应该让用户分不清“需求依据”和“处理阻塞”。
- 用户误添加了空素材目录，或目录结构已经创建但素材还没放进去；此时需要先知道“没有文件”，而不是看到多个尺寸各缺 1 张。
- 日常页面中同时出现今日数据、创建目录、尺寸预览、系统状态、上传素材、特殊命名、快捷操作、素材详情等面板，用户要自己拼出流程顺序。

## Business Value

如果这个问题值得继续 shaping，并能在可控 appetite 内完成，它应该带来这些价值：

- 减少重复导入：同一天误关重开后能更快回到工作状态。
- 降低误判成本：用户能区分 JSON 需求依据、素材校验反馈和真正阻塞处理的问题。
- 提升日常速度：页面从“找面板、点按钮”变成“按步骤走流程”。
- 减少反馈噪声：缺失、额外、尺寸预览等信息各归其位，不互相抢解释权。
- 降低空目录误判：用户能先看到素材目录本身没有文件，再决定补文件、换目录或重新校验。
- 降低后续迭代风险：先明确状态语义，再决定是否改布局、缓存、提示或处理按钮启用规则。

## Evidence

来自 2026-06-09 的用户反馈：

- “软件在处理添加文件后，进行处理文件，应该不需要被json所影响，json是给你看的，页面上缺失，增多的反馈是给我看的。”
- “json导入后，需要记忆今日导入，每次失误关掉再打开，还得重新导入一次json。”
- “导入json，尺寸预览不要做反馈，每次导入json，尺寸预览对应的尺寸就都点亮了。”
- “日常页面的布局我觉得有些繁琐了，直接做成引导式的流程最好。”

来自 2026-06-11 的用户反馈：

- 用户上传素材目录后，目录内还没有素材文件；点击校验后，详情逐条显示多个尺寸“缺 1 张”。
- 用户反馈：“上传素材后，文件内还没有文件，我点击校验后，显示缺1张，这显示错误了吧，没有文件直接就写缺失文件怎么样？”
- 这说明“空目录”和“某尺寸数量不足”在用户心智里是两个不同问题，页面应该优先表达空目录状态。
- 用户进一步明确：“软件的json只保留24小时，直接以现实世界时间为准，明天打开就重新导入。”
- 这说明“记忆今日导入”不是长期记忆，也不是永久恢复工作区；它只服务当天误关、重开、短时间继续处理的日常流程。

来自代码检查的证据：

- `src/renderer/src/App.tsx` 中 `projectsList`、`jsonFileName`、`selectedSizes` 是日常流程的 React 内存状态；启动时会从本地配置恢复用户信息、工作流设置、系统设置、工作区设置、快捷键、历史记录、通知记录和日常布局，但没有恢复今日导入的 `projectsList` / `jsonFileName`。
- `src/renderer/src/App.tsx` 的 `handleChangeJson` 导入 JSON 后会解析 `projects`，设置 `jsonFileName`，并把 JSON 中出现的尺寸收集到 `selectedSizes`，所以尺寸预览会在导入后自动点亮对应尺寸。
- `src/renderer/src/App.tsx` 的 `addFolders` 添加素材目录后会调用 `fs.readProjectSizes`，如果检测到目录尺寸，也会覆盖 `selectedSizes`。这说明同一个 `selectedSizes` 同时承载了 JSON 需求尺寸、目录检测尺寸和用户手动勾选。
- `src/main/index.ts` 的 `dialog:openJson` 只负责打开文件、读取并返回 `parseRequirementJson` 结果，没有持久化“今日导入”状态。
- `src/main/requirements.ts` 已经把 JSON 规范化为 `projects`、`sizes`、`requirements`、`requiredQuantity`、`warnings` 等结构，说明系统有足够数据作为内部需求依据，但目前这个依据没有跨重启留在日常流程中。
- `src/main/index.ts` 的 `fs:startValidation` 会根据目标需求生成 `missing` 结果；`src/renderer/src/validationPresentation.ts` 会把结果分成 blocking、missing、extra、passed。已有展示模型能区分“阻塞问题”和“用户反馈”，但日常页面的流程表达还没有把这些状态讲得足够清楚。
- `src/main/index.ts` 的 `fs:startValidation` 先通过 `collectMediaFiles` 收集可校验媒体文件，然后对 `targetRequirements` 生成 missing 结果。若素材目录没有任何媒体文件，当前流程仍会按每个需求尺寸生成数量缺口，前端就会显示多行“尺寸 缺 1 张”。
- `src/renderer/src/views/DailyWorkspace.tsx` 的 missing 行标题会把 `targetSize` 和 `missingCount` 拼成“尺寸 缺 N 张”。这适合“已有部分素材但数量不足”的场景，不适合“目录完全没有素材”的场景。
- `src/renderer/src/views/DailyWorkspace.tsx` 使用左右两栏和可拖拽面板：今日数据、创建目录、尺寸预览、系统状态、上传素材、特殊命名、快捷操作、素材详情。这个结构偏面板库，符合用户说的“布局繁琐”。
- `src/renderer/src/views/DailyWorkspace.tsx` 的主视图顶部右侧放了设置、历史和语言等操作。后续 shaping 如果重做引导式流程，需要继续遵守项目 UI 指南：避免把按钮放在应用右上角，防止被系统通知遮挡。

## Clarified Constraints

- JSON 今日导入状态只保留 24 小时内，不做长期保存。
- 时间判断以现实世界时间为准，也就是本机当前日期/时间；不是按应用运行时长、窗口会话或手动清理来判断。
- 跨到明天再次打开软件时，应视为今日导入已过期，需要用户重新导入 JSON。
- 这个约束只针对日常页的需求 JSON 工作上下文，不影响历史记录、通知记录、用户设置和命名模板等长期配置。

## Appetite

Medium Batch（2-3 个会话）。

理由：如果只记住 JSON 文件名或隐藏尺寸预览，这是 Small Batch；但这个问题横跨状态持久化、日常流程信息架构、尺寸状态语义、校验反馈语义和按钮启用规则。它不应该扩成全应用重设计，但也不能只修一个点，否则 JSON、尺寸预览和处理按钮的边界仍然会继续混在一起。

## Work To Clarify During Shaping

后续 shaping 需要回答这些问题：

1. “今日导入”具体保存什么：解析后的需求数据、JSON 文件路径、文件名、导入时间，还是一份快照。
2. 导入状态过期时如何提示：启动时显示“今日未导入”，还是显示过期 JSON 名称并要求重新导入。
3. 如果原 JSON 文件被移动、删除或内容变化，恢复时应该继续使用快照，还是提示用户重新确认。
4. `selectedSizes` 是否应该拆成不同语义：需求尺寸、素材目录检测尺寸、用户手动选择尺寸。
5. 尺寸预览在导入 JSON 后应该展示什么：只读需求摘要、可编辑目标尺寸、素材目录匹配状态，还是后续步骤中的校验结果。
6. 缺失、额外、非需求素材反馈应该出现在哪个步骤，哪些只提示用户，哪些真正阻止继续处理。
7. 空素材目录应该如何表达：全局状态写“缺失文件”、详情中只显示一条“素材目录为空”，还是同时保留总缺口统计。
8. 空目录、部分缺尺寸、尺寸错误、非需求素材的优先级如何排序，避免多个反馈同时出现时互相打架。
9. “处理文件不被 JSON 影响”在用户语境中具体指哪一步：添加素材、校验、重命名、格式处理，还是日常流程里的继续按钮。
10. 引导式流程应包含哪些固定步骤：导入需求、创建/选择目录、添加素材、校验反馈、重命名、完成归档。
11. 特殊命名、手搓命名、历史、设置等低频或分支操作如何安放，既不打断主流程，也不放在应用右上角。
12. 是否保留现有可拖拽布局设置；如果保留，它在引导式流程中是否降级为高级设置而非首屏心智。

## Non-Goals For This Frame

- 不重写 JSON 解析 schema。
- 不重写插件抓取逻辑。
- 不改变现有校验算法的核心判断。
- 不扩大到整理页、格式处理页或设置页的完整重设计。
- 不在 framing 阶段决定具体缓存方案、布局方案或数据迁移方案。
- 不单独为“空素材目录”做一次独立热修；它应并入 005 的日常流程反馈语义一起 shape 和修改。
- 不把所有反馈都变成弹窗或通知；本 frame 只锁定反馈职责混乱的问题。
- 不把尺寸预览简单删除，除非 shaping 证明它不再服务主流程。

## Frame Statement

> If we can shape this into something doable and execute within a Medium Batch,
> it will make OpenFlow's daily workflow remember today's requirement context,
> separate JSON-as-system-input from user-facing material feedback, and turn the
> daily page into a guided flow that reduces repeated imports and decision noise.
