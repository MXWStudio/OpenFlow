# Frame: 校验详情降噪与异常优先

**Record ID**: 002  
**Feature ID**: 002-validation-details  
**Created**: 2026-06-01  
**Status**: Shipped — 2026-06-02

---

## Problem

开始校验后，当前“素材详情”把所有校验结果按文件逐行展开。它能展示数据，但没有回答用户最关心的问题：

- 现在能不能重命名？
- 如果不能，卡在哪里？
- 是缺素材、尺寸不符、读取失败，还是 JSON 需求本身有问题？
- 每个异常需要用户做什么？
- 已通过素材是否只是背景信息，而不是当前要处理的重点？

真实使用时，一堆“已通过”行会占据主要视觉空间，异常行反而被淹没。用户需要滚动、扫表、自己归纳缺口，才能知道下一步该补几张图、删哪些错尺寸文件、还是调整需求数据。

当前 workaround 是用户自己在详情表里找红色/黄色状态，再结合文件夹和 JSON 需求人工判断。这个过程在素材量稍大时非常累，也容易漏看。尤其当插件抓取少了、抓取多了，或实际素材凑不够时，用户往往要到命名前才意识到需求和素材不一致。

## Affected Segment

受影响的是 OpenFlow 日常主流程用户，尤其是以下场景：

- 每个项目有多个尺寸、每个尺寸有多套素材。
- 素材数量较多，校验后会出现大量通过项。
- JSON 来自网页插件抓取，存在抓多、抓少、字段不准的风险。
- 用户需要快速判断是否可以执行重命名，而不是阅读完整明细表。

这不是一个“好看一点”的问题，而是主流程中决策信息被噪声淹没的问题。

## Business Value

如果解决这个问题，OpenFlow 的校验步骤会从“列出所有结果”变成“指导用户下一步操作”：

- 减少用户扫表时间。
- 降低漏看异常、误判可以命名的风险。
- 让插件抓取错误更早暴露。
- 让数量不足、尺寸错误、读取失败的处理路径更清楚。
- 为后续“需求修正面板”或“忽略缺口后继续”打基础。

## Evidence

来自 2026-06-01 的实际测试反馈：

- 用户创建今日目录后，输出目录曾被自动加入上传素材列表，导致上传素材区域出现大量目录噪声。这个问题已在 001 follow-up 中修正，但暴露出“系统自动状态不应增加用户清理负担”的原则。
- 校验一个需要 5 套素材的项目时，删除 `1080*607`、`1080*170` 的若干图片后，系统能识别数量不足，但详情区原本只显示“缺失/暂无素材”，不够明确。
- 后续已临时改进为显示 `缺 N 张`、`需要 X / 已有 Y`，但详情表仍把大量已通过行和异常行混在一起，视觉重点仍不理想。
- 用户明确反馈：“一堆已通过是不是要弱化，这样详情列出来看起来好多，好乱，一眼看不到重点。”

相关代码位置：

- `src/renderer/src/views/DailyWorkspace.tsx`：素材详情、分组、状态摘要、底部校验/重命名操作入口。
- `src/renderer/src/StatusBadge.tsx`：单行状态展示。
- `src/renderer/src/App.tsx`：校验结果、异常判断、重命名可用状态。
- `src/main/index.ts`：校验结果数据结构与 missing 结果生成。

## Appetite

Small Batch（1 个会话）。

理由：这个问题应聚焦在校验详情的信息架构和决策表达，不应扩展成完整 UI 重构，也不应顺手做插件抓取重写。目标是让现有校验结果更容易被用户理解和处理。

## Work To Clarify During Shaping

后续 shaping 需要回答这些问题：

1. 校验详情中，哪些信息必须默认展开，哪些应该折叠。
2. 异常的优先级如何排序：读取失败、尺寸不符、数量不足、通过项。
3. 已通过素材应该如何弱化：只显示统计、默认折叠，还是按尺寸汇总。
4. 顶部状态卡应该展示哪些关键数字：总缺口、异常尺寸数、可重命名素材数。
5. 用户发现 JSON 抓多/抓少时，当前阶段应提供什么入口：重新导入、手动调整尺寸、忽略缺口，还是标记需求有误。
6. “允许先重命名已有素材”的风险提示应该出现在哪里。

## Non-Goals For This Frame

- 不重写校验算法。
- 不重写插件抓取逻辑。
- 不做全局 UI 大改版。
- 不设计完整需求编辑器，除非 shaping 判断必须给一个极小入口。
- 不改变 001 已建立的 JSON schema 和数量校验基础。

## Frame Statement

> If we can shape this into something doable and execute within a Small Batch,
> it will make validation results action-oriented instead of table-noisy,
> so users can immediately see what blocks renaming, what can be ignored,
> and what needs to be fixed before continuing.
