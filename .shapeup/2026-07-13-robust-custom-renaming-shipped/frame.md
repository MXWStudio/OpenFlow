# Frame: 稳定且可管理的自定义重命名

**Feature ID**: 2026-07-13-robust-custom-renaming
**Created**: 2026-07-14
**Status**: Shipped — 2026-07-14

---

## Problem

OpenFlow 的常规命名目前可以工作，但团队一旦在日常页面启用“手搓命名”等特殊模式，设置中的对应模板可能没有真正作用到文件名。用户在自定义文本字段中手动输入的内容也可能不出现在最终名称中，造成界面所见模板与实际执行规则不一致。

这一问题发生在团队最需要应对临时命名要求的时候：用户已经在设置中配置字段并回到日常页面开启相应模式，却无法确认软件会采用哪一份模板。失败后只能降级到常规命名，再人工处理名称；这削弱了自定义模板本应提供的效率和可信度。

当前模板页把六类模板连续堆叠在同一页面中，主要依靠文字标题和小徽标区分。用户需要花费精力查找“常规 / 特殊 / 手搓”以及“视频 / 图片”的对应模板，团队成员也更容易改错目标模板。

## Affected Segment

- OpenFlow 的团队共同使用者，而非单一熟悉代码或配置结构的个人。
- 需要在常规规则之外处理临时、活动、渠道或项目特殊命名要求的素材生产人员。
- 对稳定批量处理有要求、不能接受应用卡住或静默使用旧规则的用户。

## Business Value

- 避免特殊命名失败后退回常规命名并人工二次修改，减少重复劳动。
- 降低团队成员改错模板、使用旧模板或产出错误文件名的概率。
- 让临时命名要求可以在软件内完成，提升文件的管理、检索和交付一致性。
- 建立可重复验证的重命名质量基线，使团队能够信任批量操作而不必逐个检查文件。

## Evidence

### 用户反馈

- 日常页面开启“手搓命名”后，文件命名不起作用。
- 设置中“自定义文本”字段输入的内容没有进入最终名称。
- 常规命名正常，特殊命名失败时团队只能降级处理。
- 设置页查找对应模板费力，需要在布局、颜色和排版上增强区分。
- 最终验收要求是稳定、高度自定义，并由开发侧主动准备测试；真实素材可以作为补充，但不应成为自动验证的前提。

### 代码核查

- `src/renderer/src/App.tsx` 执行重命名前优先从独立的 `renameTemplates` 存储键读取模板，而不是直接使用当前内存中的 `workflowSettings.renameTemplates`。界面状态与旧存储值可能发生分叉，这与“刚设置的自定义文本或手搓模板没有生效”一致。
- `src/renderer/src/views/SettingsWorkspace.tsx` 使用 500ms 延迟保存，组件卸载时会清除待执行保存。如果用户修改模板后很快返回日常页面，最后一次修改可能没有写入存储。
- 同一模板同时保存在 `workflow.renameTemplates` 和顶层 `renameTemplates` 两处，缺少单一可信来源。
- `src/main/index.ts` 的冲突循环只修改 `Sequence`。当模板为空、是固定文本或不包含序号字段时，重名后生成结果不会变化，循环可能永远不结束，页面会持续显示重命名中。
- 空模板和缺失模板会先退化成 `untitled`（随后经过路径清理），而不是在执行前给出明确、可恢复的错误。
- 尺寸解析与重命名目录识别接受的分隔符集合不一致，部分合法目录结构可能被静默跳过。
- 当前模板编辑器支持增删和替换字段，但不支持直观重排，也没有模板名称、应用状态和实际批次结果的清晰辨识。
- TypeScript 检查和现有 51 项自动化测试通过，但没有测试重命名执行、手搓/特殊模式选择、设置持久化、固定模板冲突、部分失败或降级行为，因此现有绿色测试不能证明该功能稳定。

## Appetite

**Big Batch（4–5 个工作会话）**

理由：问题横跨模板数据模型、设置持久化、主进程文件操作、失败降级、自动化测试和设置页信息设计。投入上限应覆盖真实文件系统集成测试与 UI 验收，而不只修复单个手搓开关。

## Frame Statement

> 如果能在 4–5 个工作会话内，把特殊/手搓模板从设置到实际文件操作的链路变成一致、可降级、可自动验证且易于团队辨识的工作流，就能让团队可靠应对临时命名要求，并显著减少人工返工与错误交付。
